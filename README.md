# PZ Config Panel

Private V1 web panel for one vanilla Project Zomboid B42 server on the same Ubuntu host.

This release edits the existing config files generated by the server:

- `<PZ_SERVER_NAME>.ini`
- `<PZ_SERVER_NAME>_SandboxVars.lua`

It does not expose the panel publicly, manage mods, back up worlds, update the game server, or add RCON/player administration yet.

## Current Baseline

Verified VPS baseline on May 21, 2026:

| Surface | Current value |
|---|---|
| Game install | `/home/steam/pz_server` |
| Game service | `project-zomboid.service` |
| Game server profile | `servertest` |
| Game config directory | `/home/steam/Zomboid/Server` |
| Panel deploy path | `/opt/pz-config-panel` |
| Panel service | `pz-config-panel.service` |
| Panel env file | `/etc/pz-config-panel.env` |
| Panel bind target | `127.0.0.1:3210` |

## What It Does

- Shows every existing setting parsed from `server.ini` and `SandboxVars.lua`.
- Uses known controls for common booleans, numbers, enums, and sensitive fields.
- Keeps unknown settings visible with generic controls.
- Saves only existing keys after a diff review.
- Masks password-like values on read.
- Keeps `Mods` and `WorkshopItems` read-only until a dedicated mod manager exists.
- Creates per-file backups before saves and restores, with last-20 retention.
- Uses revision checks so an old browser view cannot overwrite a newer file.
- Shows `Online` when the configured `systemd` unit is `active / running`, otherwise shows `Offline`, and asks for confirmation before restart.

V1 reads and writes config files on disk. After a save, the restart banner means the file changed and the server may need to load it again. V1 does not yet compare disk config against sandbox values loaded inside the running game process.

## Local Run

Requirements:

- Node.js 18 or newer
- Existing Project Zomboid B42 config files for the configured server profile

Install dependencies, export local environment values, and start the localhost panel:

```bash
npm install
cp .env.example .env
# Edit .env for the local or VPS paths you are testing.
set -a
. ./.env
set +a
npm start
```

Open `http://127.0.0.1:3210`.

The server reads settings from environment variables. Defaults are localhost-only:

| Variable | Default | Purpose |
|---|---|---|
| `PANEL_HOST` | `127.0.0.1` | Panel bind address |
| `PANEL_PORT` | `3210` | Panel HTTP port |
| `PZ_CONFIG_DIR` | `/home/steam/Zomboid/Server` | Directory containing PZ config files |
| `PZ_SERVER_NAME` | `servertest` | Single server profile name |
| `PZ_PANEL_BACKUP_DIR` | `<PZ_CONFIG_DIR>/.pz-config-panel-backups` | Config backup directory |
| `PZ_SYSTEMD_UNIT` | `project-zomboid.service` | PZ server system unit to inspect and restart |

## VPS Deployment

The deployment examples live in [`deploy/`](deploy/).

1. Create `/opt/pz-config-panel` on the VPS and make it owned by `steam`.
2. Upload `package.json`, `package-lock.json`, `src/`, `public/`, `deploy/`, and `README.md` into that directory.
3. Install Node dependencies there with `sudo -u steam npm install --omit=dev`.
4. Copy `deploy/pz-config-panel.env.example` to `/etc/pz-config-panel.env` and adjust the paths and server profile name.
5. Install `deploy/project-zomboid.service` as `/etc/systemd/system/project-zomboid.service` if the current vanilla server is not already managed by a system service. Adjust `WorkingDirectory` and `ExecStart` if the server startup command differs.
6. Install `deploy/pz-config-panel.service` as `/etc/systemd/system/pz-config-panel.service`.
7. Install `deploy/pz-config-panel.sudoers` as `/etc/sudoers.d/pz-config-panel` with mode `0440`, then validate it with `visudo -cf`.
8. Reload and enable the services:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now project-zomboid.service
sudo systemctl enable --now pz-config-panel.service
```

The panel status check uses `systemctl show`. The restart action runs only:

```bash
sudo -n systemctl restart project-zomboid.service
```

The provided sudoers snippet grants that restart path to `steam` and nothing broader. Do not set `NoNewPrivileges=true` on the panel unit while this V1 restart path uses `sudo`; systemd will block that sudo escalation before sudoers can apply.

Useful VPS checks:

```bash
sudo systemctl status project-zomboid.service --no-pager
sudo systemctl status pz-config-panel.service --no-pager
curl http://127.0.0.1:3210/api/server/status
```

## Private Access

The panel binds to `127.0.0.1` by default and has no login in V1. Use a private path such as an SSH tunnel:

```bash
ssh -L 3210:127.0.0.1:3210 your-user@your-vps
```

Then open `http://127.0.0.1:3210` on your own machine.

Opening Project Zomboid game ports or configuring VPS/firewall port forwarding is separate from this panel. Do not expose the panel port directly to the public internet as shipped.

## API

The UI uses the same-origin JSON API:

- `GET /api/config/ini`
- `PATCH /api/config/ini`
- `GET /api/config/sandbox`
- `PATCH /api/config/sandbox`
- `GET /api/config/backups?file=ini|sandbox`
- `POST /api/config/backups/:backupId/restore`
- `GET /api/server/status`
- `POST /api/server/restart`

Save requests contain:

```json
{
  "revision": "sha256-of-loaded-file",
  "changes": {
    "MaxPlayers": "24"
  }
}
```

Only changed keys already present in the source file are accepted.

## Sandbox Verification Boundary

For a saved sandbox change, V1 can prove:

1. The diff was accepted for an existing `SandboxVars.lua` key.
2. The file on disk contains the saved value.
3. A backup exists.
4. The configured game service restarted or is online.

V1 cannot yet prove the running game process is using that exact sandbox value. A future runtime verification path should use an in-game/RCON/bridge surface; the `zomboid-control-panel` reference under `repos/` includes a `PanelBridge` sandbox introspection path worth evaluating.

Run the automated test suite:

```bash
npm test
```

Manual VPS smoke test:

1. Start the B42 server once so the profile config files exist.
2. Point `/etc/pz-config-panel.env` at that `Server` directory and profile name.
3. Reach the panel through the localhost tunnel.
4. Change a harmless existing setting, review the diff, and save.
5. Confirm a backup appears in the backup rail.
6. Restore that backup and confirm the file value returns.
7. Confirm status is visible and restart requires confirmation.
